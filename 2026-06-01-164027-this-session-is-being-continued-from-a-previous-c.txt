  Hi Prody — first, thank you for taking the time to actually go through the    
  repo and docs. This is exactly the kind of feedback I was hoping to get       
  because it's coming from the perspective of a potential adopter rather than a 
  casual observer.                                                              
                                                                                
  A lot of what you called out is fair, and in several places you're already    
  pointing at the same questions we're actively working through.                
                                                                                
  On prompt caching:                                                            
                                                                                
  I don't view Kosh as a replacement for Anthropic/OpenAI prompt caching. In    
  fact, I'd expect most production deployments to use both.                     
                                                                                
  The distinction I'm currently working with is:                                
                                                                                
  - Prompt caching reduces the cost of retransmitting the same prompt.          
  - Kosh aims to reduce the need to transmit that prompt in the first place.    
                                                                                
  If a workflow repeatedly sends 50k tokens of context, caching can make that   
  cheaper. Kosh's long-term goal is to determine whether those 50k tokens were  
  needed at all.                                                                
                                                                                
  The other area where I think Kosh is different is tool traffic. Prompt        
  caching doesn't help with repeated repository exploration, repeated file      
  reads, repeated MCP chatter, or repeated context assembly. A large part of    
  Kosh's focus is eliminating those turns entirely.                             
                                                                                
  That said, I agree that the positioning needs to be sharper because "token    
  optimization" immediately invites the caching comparison.                     
                                                                                
  On the benchmark:                                                             
                                                                                
  You're reading it correctly.                                                  
                                                                                
  The current benchmark is a payload-reduction benchmark, not a billed-token    
  benchmark.                                                                    
                                                                                
  The reason we started there was to isolate Kosh's primitives themselves       
  (leasing, batching, signatures, composition, etc.) from model behavior. Early 
  attempts with small models ended up measuring model quality more than Kosh.   
                                                                                
  I don't consider the current benchmark the final answer.                      
                                                                                
  The benchmark I want next is exactly what you described:                      
                                                                                
  - Real agent session                                                          
  - Real API                                                                    
  - Prompt caching enabled in both arms                                         
  - Same task                                                                   
  - Same model                                                                  
  - Measure:                                                                    
    - billed tokens                                                             
    - latency                                                                   
    - tool calls                                                                
    - task success                                                              
                                                                                
  I think that's the benchmark that will either validate or invalidate the      
  thesis.                                                                       
                                                                                
  On dereferencing:                                                             
                                                                                
  This is probably the area where the docs are weakest today.                   
                                                                                
  You're right that "injects locally" can sound suspiciously like "moves the    
  tokens somewhere else."                                                       
                                                                                
  The architecture is evolving a bit, but the direction we're moving toward is: 
                                                                                
  1. Context gets represented as leases, packets, and signatures.               
  2. Kosh determines the minimal context required.                              
  3. Only that minimal context gets materialized for the model.                 
                                                                                
  The key question is not "can I replace 500 tokens with 5?"                    
                                                                                
  The key question is:                                                          
                                                                                
  "Can I avoid materializing 49,500 of the original 50,000 tokens entirely?"    
                                                                                
  We're actively building toward deterministic context planning rather than     
  simple alias expansion, and I think a concrete pipeline diagram would help a  
  lot here.                                                                     
                                                                                
  On pairing savings with quality:                                              
                                                                                
  Completely agree.                                                             
                                                                                
  A savings number without a quality number is incomplete.                      
                                                                                
  My concern is that many context-reduction systems quietly degrade outcomes    
  while looking great on cost charts.                                           
                                                                                
  Long term I want every benchmark to report something like:                    
                                                                                
  - Tokens Saved                                                                
  - Tool Calls Avoided                                                          
  - Latency Reduced                                                             
  - Task Success                                                                
  - Context Accuracy                                                            
                                                                                
  Because if Kosh saves 90% of tokens but causes a 20% drop in task success,    
  that's not a win.                                                             
                                                                                
  One thing I'd add to your list is that we've recently pivoted the             
  architecture away from "compression" and toward what we're calling            
  deterministic context planning.                                               
                                                                                
  The newer work is focused on:                                                 
                                                                                
  Fingerprint → Lease → Context Signature → Similarity → Composition → Planning 
                                                                                
  The hypothesis is that most agent workflows spend a lot of time rediscovering 
  context they already possess.                                                 
                                                                                
  If we can reliably identify and compose the minimal context needed for a      
  task, the token savings become a side effect rather than the primary          
  mechanism.                                                                    
                                                                                
  Anyway, I genuinely appreciate the thoughtful critique. Most of the points

  Deep Research Report: Kosh Phases 4–9 — Prior Art & Architecture

  1. Transparent MCP Proxy (Phase 6)

  It's already proven and buildable deterministically.

  - mcpwall (github.com/behrensd/mcpwall, v0.2.0, Feb 2026) — bidirectional
  stdio JSON-RPC proxy sitting between Claude Code/Cursor and MCP servers. YAML
  rules, first-match-wins, zero LLM, zero cloud. Explicitly guarantees "Same 
  input + same rules = same output, every time." Supports
  allow/deny/redact/log-only on both inbound tool calls and outbound responses.
  This is the exact architecture Kosh Phase 6 needs. Kosh's advantage: add
  caching + deduplication + gain tracking on top.
  - mcp-audit (P4ST4S/mcp-audit) — transparent Go proxy that intercepts, signs,
  and audits all MCP tool calls without modifying client or server. For stdio:
  spawns upstream as subprocess. For HTTP: acts as intermediary. Audit log
  pattern directly applicable to Kosh's gain tracking.
  - mcp-context-proxy (samteezy/mcp-context-proxy) — similar proxy but requires 
  an LLM as compression backend. Not compatible with Kosh's no-LLM constraint,
  but the conditional-threshold architecture (skip compression under 1000
  tokens) is worth borrowing for Kosh's cache-hit decision logic.

  Key finding: The MCP JSON-RPC methods to intercept are tools/call,
  resources/read, and prompts/get. Stdio proxy spawns upstream as subprocess,
  wraps stdin/stdout.

  ---
  2. Deterministic Context Planning (Phase 4)

  Strong prior art, and the research validates your constraint.

  - SWE-ContextBench (arxiv 2602.08316, May 2026, 1,100 tasks / 51 repos / 9
  languages): "Accurately summarized and retrieved previous experience 
  significantly improves resolution accuracy and reduces runtime and token 
  cost." Critically: "Poorly chosen context provides limited or negative 
  benefits — not neutral ones." This validates Kosh's thesis that wrong context
  actively hurts.
  - SpareCodeSearch (arxiv 2510.12948, Oct 2025): keyword search (no GPU, no
  embeddings) scores 0.748 chRF on the JetBrains/Mistral Code Context
  Competition Kotlin track. Deterministic retrieval is competitive with 
  embedding-based approaches for code context selection.
  - tree-sitter + property graph (lean-ctx, 2.2k stars, Rust binary on
  crates.io): Tree-sitter AST extraction across 18 languages + multi-edge code
  graph (imports/calls/exports/type_ref). Reports 10x token reduction vs
  file-exploration agents, 2.1x fewer tool calls across 31 real repos. This is
  the prior art for Kosh's deterministic context planner — kosh suggest mapping
  task → symbols via the import graph.
  - Size-tier classification: Deterministic file-tier system (small <100 lines /
  medium 100-499 / large 500-1999 / very_large 2000+) with predefined per-tier
  strategies achieves 60-85% token reduction across Read/Grep/Glob/Bash tool
  interceptions. Zero ML.

  ---
  3. Fact Memory (Phase 5)

  TSV-first is right. SQLite FTS5 when you need search.

  - context-mode: SQLite FTS5 + BM25 + Porter stemming (headings weighted 5x) +
  Reciprocal Rank Fusion with trigram substring matching + Levenshtein typo
  correction. 98% context reduction (315KB → 5.4KB). Playwright snapshots:
  56.2KB → 299B (99%). All deterministic, no embeddings.
  - Single-file SQLite with 4 kernels (truth/archive/ontology/promotion):
  Sub-40ms p95 latency on 120MB / ~4,000 session entries on M2 Mac. No GPU, no
  network. This is the architecture for Kosh's fact memory — truth table for
  architecture decisions, archive for past investigations.
  - memweave — uses hybrid BM25 + vector (0.7 vector weight). Incompatible with 
  Kosh's no-embeddings constraint. Useful negative example: their
  SQLite-as-rebuildable-index pattern (Markdown as source of truth, SQLite
  always reconstructible) is worth borrowing even if the retrieval mechanism
  isn't.
  - Hindsight (arxiv 2512.12818, Dec 2025): 4-network agent memory (world facts
  / agent experiences / synthesized entity summaries / evolving beliefs with
  confidence scores). The confidence-score-per-fact design maps directly to
  Kosh's Phase 5 fact format: fact \t confidence \t source \t created_at.

  ---
  4. Token Economy Platform (Phase 7)

  The math validates the architecture.

  - Triangular cost series: In a naive 10-step agent loop, each step re-bills
  all prior context. Result: 10-step loop costs 43.3× more than a single call
  ($1.49 vs $0.03). This is why conversation-history elimination (Kosh's
  leasing) has higher ROI than per-call compression.
  - SWE-bench measurement: 30,400 of 48,400 total tokens came from tool results
  alone. 39.9–59.7% of those were removable with no performance loss. Tool
  output deduplication/filtering is the highest-leverage optimization — not
  prompt compression.
  - Prompt caching gap: Cache reads cost 90% less on the cached prefix, but the
  growing conversation history is the dominant cost driver in multi-step loops
  and is not cacheable. This is the precise answer to Prody's question — now in
  the README.
  - Explicit compression every 10-15 tool calls: Achieved 22.7% savings (14.9M →
  11.5M tokens) while matching baseline accuracy. Deterministic scheduling
  outperforms per-step summarization.
  - Subagent isolation (coordinator + specialists): Reduced token consumption by
  53.7%. Relevant to Kosh's packet-per-feature model.

  ---
  5. What's Validated vs What's Refuted

  Validated for Kosh's roadmap:
  - Deterministic proxy interception is feasible and production-ready (mcpwall)
  - No-embedding keyword search is competitive for code context
  (SpareCodeSearch)
  - SQLite FTS5 is sufficient for fast deterministic fact retrieval
  - Tool result deduplication has higher ROI than prompt compression
  - Conversation history growth is the dominant cost driver, not prompt size
  - Wrong context actively hurts, not neutrally — validates minimum-context
  thesis

  Refuted / caution:
  - LLMLingua (20x compression) — requires LLM, incompatible
  - memweave — uses vector embeddings, incompatible
  - SWE-Pruner (23-54% reduction, improving success rates) — uses 0.6B neural 
  skimmer, not deterministic
  - Static compression rules yield "limited or unstable gains" across
  heterogeneous repos — validates Kosh's per-repo fingerprint approach over
  global rules
